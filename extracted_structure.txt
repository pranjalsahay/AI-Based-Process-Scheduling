P[11] (Style: Heading 1): ABSTRACT
P[12] (Style: Normal): WattWise is an enterprise-grade Smart Energy Consumption and Audit System developed to address the critical challenge of electricity tracking, baseline forecasting, and anomaly detection across multi-facility institutional campuses. Centered upon robust Database Management System (DBMS) principles, the system models physical campus hierarchies spanning buildings, floors, rooms, and electrical devices in a strictly normalized Third Normal Form (3NF) relational database. Implemented using MySQL 8.0, the persistence layer utilizes transactional ACID storage engines, relational integrity constraints, and compound B-Tree indexes on time-series telemetry. Advanced SQL features—including stored procedures, stored functions, row-level triggers, explicit cursors, and SQL window functions (LAG OVER PARTITION BY)—are deployed to transform cumulative meter readings into discrete interval consumption, prevent physical meter regressions, and detect abnormal off-hours or equipment energy spikes. The relational schema is integrated with a high-performance Python FastAPI backend and an interactive React 19 single-page application featuring a dedicated Database Studio for real-time table inspection and dynamic SQL execution. The system guarantees zero data loss, enforces role-based access security, and automates institutional energy auditing with verified sub-second analytical reporting.
P[13] (Style: Normal): Keywords: Database Management Systems, 3NF Normalization, Stored Procedures, Triggers, Cursors, Window Functions, Energy Audit.

P[19] (Style: Heading 2): 1.1 Problem Statement
P[20] (Style: Normal): Commercial buildings, university campuses, research laboratories, and large institutional facilities account for a substantial fraction of modern electrical energy consumption. In most organizations, electrical tracking remains primitive, relying on aggregated monthly utility invoices, manual pen-and-paper meter logbooks, or disconnected spreadsheets. These legacy methods suffer from critical vulnerabilities: manual data entry leads to clerical errors; spreadsheet architectures lack referential integrity, creating orphaned device logs; and monthly aggregate bills fail to illuminate granular equipment-level wastage, power factor degradation, or off-hours phantom loads. When an HVAC unit malfunctions or a server room experiences cooling failure during non-working hours, the anomaly goes undetected until catastrophic failure occurs or an inflated monthly utility bill arrives. Consequently, there is an urgent need for a robust, centralized Database Management System capable of ingesting high-frequency telemetry, enforcing schema constraints, isolating spatial consumption, and detecting abnormal usage in real time.

P[22] (Style: List Bullet): Objective 1 – Relational Schema Design: Design and normalize an enterprise relational schema to Third Normal Form (3NF) to model campus buildings, rooms, equipment sub-meters, and time-series electrical telemetry without redundancy.

P[25] (Style: List Bullet): Objective 4 – Rule-Based Anomaly Detection: Engineer automated SQL-backed anomaly rules to detect off-hours consumption, rated power exceedance, and sudden load spikes.
P[26] (Style: List Bullet): Objective 5 – Secure Full-Stack Application: Develop a modern full-stack web application with role-based access control (Admin, Auditor, Viewer) and an interactive Database Studio enabling live table inspection and parameterized query execution.
P[27] (Style: Heading 2): 1.3 Importance of DBMS
P[28] (Style: Normal): A relational DBMS is uniquely suited for enterprise energy monitoring over ad-hoc file storage or non-relational alternatives due to:
P[29] (Style: List Bullet): 1. Data Integrity: Foreign key relationships guarantee that meter readings cannot exist without a valid parent device, and devices cannot exist without a valid room. CHECK constraints reject negative power values at the engine level.
P[30] (Style: List Bullet): 2. Elimination of Redundancy: Through 3NF normalization, building names, floor areas, and tariff rates are stored exactly once. A change in building metadata instantly reflects across millions of historical readings without update anomalies.
P[31] (Style: List Bullet): 3. ACID Concurrency Control: Automated sensor ingestion and manual CSV uploads execute inside isolated transactions. Read-committed isolation guarantees that analytical audit reports reflect consistent point-in-time snapshots without dirty reads.
P[32] (Style: List Bullet): 4. High-Performance Querying: Composite B-Tree indexes on (device_id, recorded_at) permit instant logarithmic-time lookup across multi-million row telemetry tables.
P[33] (Style: List Bullet): 5. Granular Security & Auditability: Database-backed audit logs record all administrative operations, tariff modifications, and user authentications.

P[64] (Style: Heading 2): 3.4 Database Normalization
P[65] (Style: Normal): Normalization is the rigorous mathematical process of decomposing complex relational schemas into smaller, well-structured relations to eliminate redundancy and prevent insertion, update, and deletion anomalies. The step-by-step progression of the WattWise schema from an Unnormalized Form (UNF) to Third Normal Form (3NF) is detailed below:
P[66] (Style: List Bullet): 1. Unnormalized Form (UNF) to First Normal Form (1NF): In UNF, a single flat log sheet recorded building details, room tags, device names, and non-atomic comma-separated meter readings [e.g., Readings = (100.2, 102.4, 105.1)]. This violated 1NF due to repeating multi-valued groups. Decomposition to 1NF: All attributes were made atomic, repeating groups were factored into distinct child records, and a synthetic primary key (id) was established for every relation.
P[67] (Style: List Bullet): 2. First Normal Form (1NF) to Second Normal Form (2NF): A relation is in 2NF if it is in 1NF and contains no partial functional dependencies (no non-prime attribute depends on a proper subset of any candidate key). In an intermediate relation with composite key (building_code, room_number), attributes like total_floors and area_sq_m depended solely on building_code. Decomposition to 2NF: The building attributes were decomposed into the independent BUILDINGS relation, ensuring all room attributes depend on the full composite key.
P[68] (Style: List Bullet): 3. Second Normal Form (2NF) to Third Normal Form (3NF): A relation is in 3NF if it is in 2NF and contains no transitive functional dependencies (no non-prime attribute depends on another non-prime attribute: X → Y → Z). If METER_READINGS stored device_name, room_number, and building_name, the transitive chain reading_id → device_id → room_id → building_id would cause severe update anomalies (e.g. renaming a building would require updating millions of reading rows). Decomposition to 3NF: METER_READINGS strictly retains device_id as a foreign key. Derived attributes such as total_building_consumption are completely excluded from tables and calculated dynamically via SQL views.
P[69] (Style: List Bullet): 4. Boyce-Codd Normal Form (BCNF) Verification: A relation is in BCNF if for every non-trivial functional dependency X → Y, X is a superkey. In all WattWise relations, the sole determinants are the synthetic primary keys (id) or unique candidate keys (e.g. building_code, device_code), verifying full compliance with BCNF.

P[133] (Style: Heading 2): 7.2 Challenges Faced & Solutions
P[134] (Style: List Bullet): 1. Window Delta Boundary Handling: Challenge: When filtering readings by date range, the first reading of a period had no preceding row inside the WHERE clause, causing LAG() to return NULL.
Solution: Implemented a Common Table Expression (CTE) that fetches the immediate pre-boundary reading using a correlated subquery before applying the final date filter.
P[135] (Style: List Bullet): 2. Cumulative Meter Rollover Semantics: Challenge: Differentiating between an illicit negative reading and a genuine physical hardware odometer reset/rollover.
Solution: Added a source column flag ('Manual', 'Reset', 'Automated') and trigger logic that requires explicit reset flags to authorize decreasing odometer readings.
P[136] (Style: List Bullet): 3. High-Frequency Concurrent Writes: Challenge: Database deadlocks and connection starvation under simultaneous sensor ingestion.
Solution: Optimized transaction isolation levels to READ COMMITTED and configured an SQLAlchemy connection pool with 10 persistent slots and 20 burst connections.

P[138] (Style: Normal): Future enhancements could include implementing MySQL table partitioning by month (PARTITION BY RANGE (TO_DAYS(recorded_at))) to optimize query execution across years of historical readings, integrating an automated MQTT broker for direct smart breaker hardware ingestion, and implementing machine learning forecasting models inside BigQuery or Python.
